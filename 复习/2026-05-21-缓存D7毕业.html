03 · THREE PITS

三类坑 · 你的个人钩子库

Q4 的核心遗产——三个名字都是从你今日自造的具体例子里抽象出来的， 所以 D+30 的调取速度会比抄书快 5 倍。

// 性能轴
打车空载坑
没命中时 = embedding + 余弦搜索 + LLM 推理 = 双重成本，比裸跑 LLM 还慢、还贵。 命中率压测不到阈值就上线 = 负收益事故。
原型：5/14 自创"打车比喻"——叫不到车反而比走路还慢。
// 质量轴
鱼香水煮坑
余弦相似度看不出"鱼香 vs 水煮"是两种味型——它只看到"X 肉 Y"语义结构相似。 法律领域加强版："我能告他吗"语义近，但答案该完全不同。
原型：5/14 自创"点菜比喻" + 5/21 自造菜名例子。
// 安全轴
银行存款坑
"我银行存款多少"——千万用户问出来语义几乎一致，余弦 ≈ 0.99， 百分百命中 → 跨用户串答案 → 数据泄漏 + 法律事故。
原型：5/21 自造金融场景，比合同事故更具普遍性。
04 · LIFE / DEATH CHECKLIST

两道生死题 · 缓存设计前置过滤

5/13 焊的钩子，5/21 在 Q5 中用判断式句式调取——按顺序问，任何一道 NO 就拦下。

  1. 输出会不会随时间变化？　→　拦下：天气 / 新闻 / 汇率 / 法律修订
  2. 输出会不会依赖于"用户私人 / 会话上下文"？　→　拦下：上传的合同 / 个人数据 / 账户余额
  3. 通过两道题后再算经济账：估算命中率，命中率 < 阈值就别上语义缓存（防打车空载坑）。
  4. 若可缓存：再做"知识 vs 结论"分流——只缓存知识性 query，结论性 query 一律不缓存（防鱼香水煮坑）。
  5. 对涉及私人上下文的 query：单用户会话内可用提示词缓存优化（前缀复用 KV Cache），但绝不进跨用户语义缓存（防银行存款坑）。
