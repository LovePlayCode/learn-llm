A1 · Agent Loop 与 Tool Calling

2026-08-13
Agent = LLM + Tool + Looptool_call = id+name+argsToolMessage / tool_call_id无状态模型messages 工作记忆

核心概念

  • 模型申请工具（结构化 tool_call），宿主执行，结果以 ToolMessage 回写——发起权与执行权分离。
  • 模型无状态：每轮重新看完整份消息列表；循环停止的机制层信号 = AIMessage 不再带 tool_calls。
  • 记忆分两层：messages 列表（工作记忆 ≈ 内存数组）/ checkpointer（持久化 ≈ localStorage）。

打字默写检查（实录）

Q：Loop 什么时候停？

初答混了层级——语义层（任务完成）≠ 机制层（无 tool_calls）≠ 安全网（步数上限），分层后修正。

Q：tool_call 数据结构？

初答 {name, args} 且 args 写成数组——漏了 id、args 应为对象。并行调用时结果靠 id 对号入座。

Q：加"查天气"能力要改模型吗？

一次答对：不改模型，注册工具即可——能力是数据驱动。

盲点自查

消息类型曾漏掉 AIMessage（循环里"最忙"的消息）。
实践首版 createSerchWeb(result: []) 类型错误 + 运行时 TypeError——被护栏中间件接住，第一次亲手体验"错误恢复"。

实践验证

  • 新增 search_web 工具（三件套 + 注册 + demo 06 调用），模型零改动，两轮修复后全绿。
金句：Agent 是由概率模型驱动的状态机——正因为调度不确定，护栏才必须存在。

A2 · 中间件链

2026-08-13
六种钩子wrap = 洋葱包裹顺序即契约横切关注点GraphBubbleUp 放行

核心概念

  • 中间件统一处理横切逻辑（消毒/错误/限流/澄清），不侵入业务代码。
  • wrap\* 包裹调用的进与出（可改请求、处理响应、决定放行）；before\*/after\* 是单点打桩。
  • 五层顺序：消毒（双 wrap）→ 错误恢复（wrapToolCall）→ 循环检测（afterModel）→ 子代理限流（afterModel）→ 澄清（wrapToolCall，必须最后）。
  • interrupt() 借异常通道传播控制流；错误恢复必须 isGraphBubbleUp 放行，否则 HITL 被吞。

打字默写检查（实录）

Q：澄清不排最后会怎样？

初答"interrupt 会正常运行"——错；修正：澄清最内层，interrupt 须穿过外层 try/catch，吞掉即 HITL 失效。

Q：新增"耗时统计"中间件怎么设计？

钩子与位置决策全对：wrapToolCall；是否给失败调用计时决定相对错误恢复的内外。

盲点自查

曾把 wrap\* 理解成"调用前做逻辑"，漏了出侧。
曾复述教师原话代替自己的推理（流畅性错觉）；曾漏题（规则：每题必答，不会写"不会"）。
高光：主动反问"澄清排最外层没人能吞异常啊？"——逼出"守卫在外/业务在内、免决策契约、放行规则通用"三条更深理由。

实践验证

  • 自建 tool-timing 中间件（try/finally 覆盖失败调用），插入错误恢复之内并注释理由；demo 02 中 flaky 的失败耗时照样打出。
金句：顺序契约的价值不在"这次跑通"，在于让错误的组合在结构上不可能出现。

A3 · State 与 Reducer

2026-08-13
显式合并Reducer<T>按 key 分级fail-closed缺席 ≠ 清空stateSchema 接线

核心概念

  • 同轮并发写同一 key，合并规则必须显式：(existing, incoming) => merged，缺席是合法输入。
  • 策略分级：可合并 → 去重/后写覆盖；不可调和 → 抛错（fail-closed）。
  • 协议：null/undefined = 没碰；{} = 显式清空。channel 声明的类型 = reducer 返回值契约。
  • 孤儿 reducer：挂进 Annotation.Root 并传给 createAgent 的 stateSchema 才接通。

打字默写检查（实录）

Q：学前预测两场景策略？

未读先中："覆盖 / 报错，分开讨论"——策略直觉满分。

Q：reducer 签名？

初版 (old, action) => action()——action 不是函数、替换 ≠ 合并；两轮修正后写出泛型 Reducer<T>。

盲点自查

mergeTodos 首版注释承诺 null 分支但代码没做——注释承诺必须代码兑现。
修复时误把返回值加宽为 null，违反 channel 契约（typecheck 红）——类型改动先看声明边界。

实践验证

  • 实现 mergeTodos + 挂入 demo 07 ThreadState + 场景 D（同 id 覆盖 / 新 id 追加 / null 缺席），三轮迭代全绿。
金句：合并策略按业务语义分级；冲突时宁可报错也不猜。

A4 · 上下文工程

2026-08-14
静态 prompt + 动态注入prefix cache三层渐进披露lost in the middle软引导 vs 硬强制

核心概念

  • system prompt 全静态保 prefix cache（键 = 前缀的每个字节；TTL 分钟级；命中读取约 1 折）；日期/记忆由 DynamicContextMiddleware 注入第一条 HumanMessage。
  • "system prompt 的末尾" ≠ "前缀之外"——整个 system prompt 都在前缀里（如同 URL 末尾的查询参数照样改变缓存键）。
  • 技能三层披露：skill_index（名字+一句话）→ describe_skill（元信息）→ read_skill（正文），每层成本递增。
  • 软引导（prompt 设计）用于"失败只打折质量"的事；硬强制（代码）用于"失败即事故"的事——风险等级决定手段。

打字默写检查（实录）

Q：demo 05 里谁先谁后、谁规定的？

初答"中间件控制"——与"动态注入走中间件"装反了；修正：披露顺序靠 prompt 软引导，动态注入才走中间件。

Q：三天三请求的缓存命中几次？

主动构造场景反问后答对：命中 2 次，第一天冷启动不算。

盲点自查

软引导 vs 硬强制曾装反——记住对照表：建议性 → prompt；结构性 → 代码。
高光：主动追问供应商缓存 TTL（OpenAI 30 分钟刷新 / Anthropic 5 分钟起）——开始用成本视角看架构。

实践验证

  • 新增 weekly-report 技能 + demo 05 验证 describe→read 顺序；skill_index 自动收录，prompt 结构零改动。
金句：能力是数据，不是逻辑（A1 加工具不改模型，A4 加技能不改 prompt）。

A5 · HITL 人机协同

2026-08-14
interrupt / resumecheckpointer + thread_idCommand(goto=END)artifact.human_inputhide_from_ui

核心概念

  • 两种范式：demo 03 = interrupt() 冻结图中断、Command({resume}) 断点恢复；生产（08）= wrapToolCall 返回 Command(goto=END) 正常结束本轮，答案作为下一轮隐藏 HumanMessage。
  • 中断 = 执行现场持久化（可恢复）；return = 现场销毁。恢复靠 thread_id 找会话。
  • 结构化卡片：ToolMessage.artifact.human_input（request_id 配对、版本化、老前端降级纯文本）。
  • 两个 id 分层：thread_id 管"哪次对话"，tool_call_id 管"哪次调用"。
  • 工具是"框架可介入的协议点"——纯文本输出框架无从插手。

打字默写检查（实录）

Q：ask_clarification 的函数体为什么执行不到？

初答钩子名错（wrapModelCall）——应为 wrapToolCall：拦的是工具执行，不是模型调用。

Q：resume 的答案变成什么、挂哪个 id？

初答"挂 thread_id"——修正：变成 ToolMessage，挂 tool_call_id（A1 单号配对闭环）。

盲点自查

钩子名精确度（wrapToolCall ≠ wrapModelCall）；两个 id 的层级曾混淆。
高光：自学自建 08-hitl-end-turn.ts 对照生产实现（artifact 协议 / hide_from_ui / returnDirect 的 JS-Python 差异），实践验证提前超额完成。

实践验证

  • 08 demo：run 1 停在结构化卡片 ToolMessage；run 2 隐藏 HumanMessage 带回答入线程，模型继续——typecheck 绿、运行全对。
金句：中断借异常通道传播，但语义是"暂停信号"不是"错误"——错误处理必须放行控制流。

A6 · 子代理与护栏

2026-08-14
task 工具 = 子代理入口上下文隔离prompt 自包含afterModel 截断可观测截断

核心概念

  • 子代理 = 又一整个 Agent 循环（模型+工具+loop），隔离上下文干活，只回传摘要——保护主对话上下文。
  • task 的 prompt 必须自包含：子代理看不到主对话历史（隔离的代价与收益）。
  • 限流在 afterModel 改写消息（执行前让消息与计划一致）；执行中拦截会造成悬空 tool_call，下次模型调用被厂商 API 拒收。
  • 截断必须可观测：notice 写进消息（[subagent_limit] Kept 1/3…），模型读到后重新规划。
  • 子代理 checkpointer=False：一次性任务，失败重跑即可。

打字默写检查（实录）

Q：被截掉的 task 去哪了，模型知道吗？

初答"模型不知道"——错；截断说明追加在消息里，模型可见并可重规划（护栏动作对模型可见）。

Q：为什么 afterModel 截断而非执行中拦？

自己推出 dangling tool call 约束——生产级直觉（真实 DeerFlow 有专门的 DanglingToolCallMiddleware）。

盲点自查

纵向题首答"职责分离"是 B 层答案；A 层答案要落到"消息改写 vs 执行拦截"的配对问题。

实践验证

  • demo 04 改 maxConcurrent=1 + 补发 B/C 两轮：截断说明 → 模型补发 → 三个 task 全部完成，闭环验证通过。
金句：护栏动手时必须留痕迹——静默截断会让模型在幻觉里继续编。
