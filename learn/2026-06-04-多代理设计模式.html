① 多代理的本质定义：多个 代理 协同工作以实现 共同目标 的设计模式。

② 三种核心模式：群聊 GroupChat / 任务转接 Handoff / 协同过滤 Collaborative。

③ 群聊：多对多沟通，适合头脑风暴和交叉验证。

④ 任务转接：1 对 1 流水线，一份输入串行处理。

⑤ 协同过滤：多视角并行 + 汇总成一个综合答案（⚠️ 不是复制流水线！）。

⑥ 4 大优势：专业化 / 可扩展 / 容错 / 模块化。

⑦ 何时不用：任务简单 / 工作量小 / 单一专业能力即可。

⑧ 上下文隔离 → 服务于 专业化，归到 工程手段 层。

SECTION 02 · 三种模式对比

群聊 / 任务转接 / 协同过滤

PATTERN 01

群聊 Group Chat

多对多 · 信息透明
所有 Agent 在共享对话里讨论。适合开放性问题、头脑风暴、交叉验证。

何时用：问题没标准答案，需要多视角碰撞。

PATTERN 02

任务转接 Handoff

1 对 1 · 流水线
A → B → C 接力，每棒处理后传给下一棒。一份输入串行加工。

何时用：任务可线性拆分，每一段输入有明确下一棒。

PATTERN 03

协同过滤 Collaborative

多视角并行 + 汇总
同一个客户需求，分发给 N 个不同专长 Agent 独立分析，最后汇总成综合答案。

⚠️ 不是"复制流水线"！是 fan-out + fan-in。

三种模式的"接力图"对比

  群聊：    A ⇄ B ⇄ C    （多对多，共享对话）

  任务转接： A → B → C    （流水线，一份输入串行）

  协同过滤： 客户需求 ──┬→ 口味派 ─┐
                       ├→ 营养派 ─┤→ 汇总 → 综合推荐
                       └→ 性价比 ─┘
            （fan-out 多视角并行 + fan-in 汇总）

SECTION 04 · 多代理优势

3 个维度覆盖 4 大优势

  1. 质量维度 · 专业化（Specialization） 每个 Agent 是某个领域的"专家"，prompt / 工具集 / 模型可独立优化。同时享受"上下文隔离"——每个 Agent 不被无关上下文打扰。
  2. 规模维度 · 可扩展性（Scalability） 多个 Agent 可并行执行，整体吞吐显著提升。增加新能力 = 加一个新 Agent，不需要改老 Agent。
  3. 健壮性维度 · 容错性（Fault Tolerance） 某个 Agent 失败/超时不影响整体，可以局部重试，不需要"整链重头来过"。
  4. 工程维度 · 模块化（Modularity） 每个 Agent 边界清晰，可独立测试、独立演进、独立替换。这跟微服务火起来的理由是同一个。
SECTION 05 · 横向连接

vs 单代理 ReAct · vs 微服务架构

多代理 vs 单代理 + ReAct 循环：本质差异是什么？

① 上下文隔离：单代理所有动作（思考-行动-观察）共享同一个上下文；多代理每个 Agent 各自独立。

② 专业化：单代理是"全能选手"，多代理是"专家团队"。

③ 协调层（新增维度）：单代理无此概念；多代理必须回答"谁说话、说给谁、何时停"——这是一个全新的概念维度。

多代理 vs 微服务架构：哪里像、哪里不像？

像：都是"专业化拆分 + 协作完成"的工程哲学。模块化、可独立演进、可独立测试。

不像 · 通信：微服务用 API 契约（确定性）；多代理用自然语言/消息（LLM 解读，模糊）。

不像 · 调度：微服务的"调用谁"是代码写死；多代理的"调用谁"可能是另一个 LLM 决定的（动态）。

不像 · 错误：微服务错误是确定性的（503 / 超时 → 重试）；多代理错误是概率性的（幻觉 / 漂移 → 需要裁判 Agent 交叉验证）。

多代理 vs LangGraph 单图多节点：是同一个东西吗？

LangGraph 的 multi-agent 本质上就是把"每个 Agent 封装成 Node"。但 LangGraph 也支持"非 Agent 的 Node"（路由、工具、条件分支）。所以：每个 Agent 是 Node，但不是每个 Node 都是 Agent。

SECTION 06 · 替代方案 · 反事实思考

不用多代理还有什么办法？为什么没完全取代？

替代 01

更长上下文窗口（Gemini 1M / Claude 200k）

① 训练成本极高；② 即使长，lost in the middle 问题依然存在；③ 解决了"容量"问题，但解决不了"专业化"和"模块化"问题。

替代 02

Prompt 角色切换（同一 LLM 演不同角色）

① 没有真正的上下文隔离——前一个角色说过的话还在历史里污染下一个；② 无法并行——一次只能演一个角色；③ 同一模型能力分布固定，难真正"切换"成专家。

SECTION 07 · 反向决策

什么时候不该用多代理？

  1. 任务简单明了 能用一个 prompt + 一组工具搞定时，多代理是过度设计。
  2. 工作量小 没有并行需求时，多代理只是徒增协调成本。
  3. 单一专业能力即可 不需要多种互补能力时，"专业化"的优势体现不出来。
  4. 误用代价（D7 必补的题） 误用多代理会带来：① 协调开销（Agent 间通信轮次暴涨）；② 调试难度（错误可能出现在协调层而非业务层）；③ 不确定性放大（多个 LLM 调用 = 多个幻觉源）。

SECTION 10 · 盲点自查

今天暴露的薄弱点（D2 / D7 重点）

⚡ 协同过滤 · 第二次复犯（必须重点跟进）

子题 3 实现题里，你又把协同过滤画成"复制 3 条流水线"——这跟你之前误解为"派活+验收"是同一个家族错误：把"协作"理解成"复制"，没抓到"多视角并行 + 汇总"的核心。D2 必须用一道实现题再考一次。

设计动机偏"痛点驱动"

"为什么是这样设计"这一题，回答还是停在"单代理不行所以多代理"——这是被动逃避视角。需要补上"主动选择视角"——分工带来的模块化、可测试、可演进本身就是好东西，与单代理是否有瓶颈无关。

误用多代理的"坏后果"题没答完

题 3 我问了 a) 何时不用 + b) 误用会怎样，你只答了 a)。误用后果包括：协调开销暴涨 / 错误源放大 / 调试难度上升。D7 综合题要补。

Edge vs Node 内部逻辑职责分层小混淆

实践题里把"待洗盘子数 ≥ 1"这种 Node 内部判断，错放在了 Edge 上。Edge 上的 Conditional 通常处理"流向哪里"；Node 内部判断处理"我要不要干活"。

Prompt 切换替代方案的关键点没点透

你说"无法解决根本问题"过于笼统，没说到致命的两点：① 没真正的上下文隔离（所有角色共享对话历史） ② 无法并行（一个 LLM 一次只能演一个角色）。
