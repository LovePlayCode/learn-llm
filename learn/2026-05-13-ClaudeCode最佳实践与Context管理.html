SECTION 01 ─── 核心机制

为什么 context window 决定了一切

Claude Code 不是聊天机器人。它会自己读文件、自己跑命令， 这两个动作的产物会全部塞进 context。一次调试可能消耗数万个 token——这才是 context 爆炸的真正大头。

— 现象 ─ Lost in the Middle

注意力分布不均匀

模型对 开头 和 结尾 的注意力远高于中间部分。 context 越长，重要信息越容易被埋在"中段塌陷"里被忽略。

— 后果 ─ 工程层面

效果不稳定的根因

context 越长 → 模型越容易"丢重点" → 边读边改时 context 越滚越乱 → 一旦决策点被埋进中段，就成了你感受到的"它怎么又忘了我的要求"。

SECTION 03 ─── 三工具精确分工

它们看似相似，做的动作完全不同

Time · 时间

/clear

清空当前主 context，让对话回到"刚打开"的状态。 不启动新 agent，就是把过去的脏东西扔掉。

场景：刚调完 bug，要写不相关的新功能 → /clear

Space · 空间

subagents

启动子 agent，子 agent 有自己独立的 context， 它读 30 个文件不会污染你。最后只把摘要回传给主对话。

场景：调研"项目里有没有现成的 OAuth 工具" → 派 subagent

Phase · 阶段

Plan Mode

同一个 agent，切换到只读模式。不启动新 agent， 只是禁止改文件——先想清楚，看到完整计划，再切回 Normal Mode 执行。

场景：跨 5 个文件的重构 → 先 Plan Mode 审计计划

真实分工对照表 工具 | 启动新 agent? | context 怎么处理 | 解决什么 ──────────────┼───────────────┼─────────────────────────┼────────────────────────────── /clear | ✗ 不启动 | 清空主 context | 之前的脏东西不要了 subagents | ✓ 启动 | 子 agent 独立 context | 脏活外包，主 context 别脏 Plan Mode | ✗ 不启动 | 同一 context，切换权限 | 在动手之前先审计计划
SECTION 04 ─── 今天踩过的三类坑

三个被工具拎出来的混淆

坑 1 · 把"现象"当"机制"

用"注意力分散""拎不清重点"解释 context 满载——只是换了个说法，没解释机制。修正：触达 Lost in the Middle 这个真正的物理现象。

坑 2 · 把 Plan Mode 当 subagent

说"Plan Mode 拿着计划启动另一个 agent"——这是典型的"上下兄弟"层级混乱。两者虽是兄弟（都保护主 context），但具体动作完全不同：subagent 真的另起 agent，Plan Mode 只切模式。

坑 3 · 用术语贴标签代替展开解释

"因为 lost in the middle"这种一句话答案，看起来正确，实际上没有信息量。修正：术语后面必须跟一句"它的意思是 ..."。

SECTION 05 ─── 回到工位就能用

下次开 Claude Code，先问自己这 4 件事

当前任务和上一个任务相关吗？

不相关 → 立刻 /clear。不要让上一个任务的 30 个文件污染下一个任务。

这个动作需要"读很多文件"吗？

需要 → 派 subagent。让脏活在别的 context 里干，主对话只收摘要。

这次改动跨了几个文件？

跨 ≥ 3 个文件，或我自己也不确定方案 → 先 Plan Mode 看计划，再切 Normal Mode 执行。

关键信息我放在哪里？

Lost in the Middle 提醒：把约束、目标、决策放在 prompt 的开头或结尾，不要塞中间。

SECTION 06 ─── 横向连接

这个知识和你以前学过的什么相关？

与 RAG 检索系统的相似性 —— 都是在"解决 context 太贵"
RAG 的本质是"不要把全部知识塞进 context，只在需要时检索一小段塞进去"。 Claude Code 的 subagent 思路完全一致：不要把全部探索过程塞进主 context， 只让子 agent 探索，回传一段摘要。

同一种思维：稀缺的不是知识，是 context 的"卖场货架"。
与 AI 智能体三要素的关系 —— Plan Mode 是"规划与行动分离"的实例
在 AI 智能体里，"规划（Planning）"和"行动（Action）"是两个独立要素。 Plan Mode 把这两个要素在 Claude Code 里显式拆成了两个阶段—— 这是智能体设计原则在工具层的具体体现。

不是新概念，是旧理念的工程化。
与采样（Sampling）的对照 —— 都是底层工具，不是上层方法
2026-05-11 那次踩坑：把"采样"误认为"自洽性方法"。今天这次同样的失误： 把"Plan Mode 的实现细节"误认为"启动新 agent"。

元层级的薄弱点：你倾向于把"工具/操作"当成"方法/策略"。 这是同一种思维习惯的失灵，不是两个独立漏洞。
与 AI 代理设计原则的关系 —— context 隔离是核心模式
在 AI 代理设计里，"任务隔离""职责单一"是核心原则。 subagent 就是这个原则的产物：把一个有界的探索任务交给独立 agent， 主 agent 只负责协调和决策。

下次设计自己的 agent 时，记住：不是"一个 agent 干所有事"，是"主 agent 协调子 agent"。
SECTION 07 ─── 元层级成长曲线

本次学习中，你的思维进步了什么？

"你倾向于用'短而抽象的词'封装答案，而不是用'长而具体的句子'展开答案。"

这是今天教练在你身上观察到的思维习惯。最后一轮关门复述里，你已经开始修正—— 把"Lost in the Middle"展开了一句"即关注开头和结尾大于关注中间"。 这是从"贴标签"到"讲清楚"的关键一跃。

"你打断了一个权威，问'你带我去的地方对吗'。"

中途那一问，让教练自己也修正了过深追问的方向。这个习惯比答对题更值钱—— 它在你以后自学任何东西的时候，都会救你的命。
