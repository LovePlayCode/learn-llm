01

这一节要解决什么

真实问题

正在做一个 AI 应用，要决定：要不要加缓存 加哪种 怎么加才不出事

缓存对 AI 应用是 "双倍重要"—— 既降延迟，又降成本。 传统软件查一次数据库几乎零成本；AI 应用调一次大模型要 1–3 秒，还按 Token 收费。

02

精确缓存 vs 语义缓存

EXACT CACHE

精确缓存

match · char-level
  • 比的是 字符完全一致
  • 命中 → 直接返回
  • 未命中 → 处理 + 存 + 返回
  • 典型场景：向量搜索结果缓存、产品摘要
  • 命中率 天花板低（用户措辞会变）
SEMANTIC CACHE

语义缓存

match · meaning-level
  • 比的是 意思相近
  • 三步：嵌入 → 向量搜索 → 阈值判断
  • 命中率 天花板高
  • 但 5 个坑随时翻车 高风险
  • 命中也要付 向量搜索的判断费
key insight

语义缓存的存在理由：精确缓存的命中率天花板太低。 工程师宁可冒着 5 个坑的风险，也要把低天花板捅破。

03

精确缓存的两条腿

// 新查询进来 ┌──────────────────┐ │ incoming query │ └────────┬─────────┘ ▼ 命中？ ┌───┴───┐ ▼ ▼ YES NO │ │ 直接返回 ① 真处理（调大模型 / 跑向量搜索 / 执行 SQL） │ ② 写缓存（把结果存起来） │ ③ 返回（把结果给用户） ▼ end // 算账要点： // 命中 = 纯赚（几乎零成本） // 未命中 = ① 那一笔全付 + ② 多一个写入动作
04

语义缓存的三类坑

用「上下兄弟」分层——书里把 5–7 个坑写成了散文，你要主动把它们归到三个抽屉。

QUALITY
质量类坑（判断不准）
  1. 嵌入向量质量差
  2. 向量搜索质量差
  3. 相似度度量标准不可靠
  4. 阈值难调（需反复试验）
PERFORMANCE
性能类坑（判断本身有成本）
  1. 每次查询都要跑一次向量搜索
  2. 缓存越大，搜索越慢、越贵
SAFETY
安全类坑（根本不该缓存）
  1. 用户专属查询 → 数据泄露
  2. 时效性查询 → 返回过期答案
05

"要不要加语义缓存"决策清单

在工位上真正用得上的判断顺序——前两条是前置过滤器（不通过则直接否决），后三条是性价比评估。

  1. 用户的查询是不是「用户专属」？答案里有没有夹带个人数据？
    前置过滤器 · 个人化查询若被误缓存 → 数据泄露事故
  2. 查询的答案有没有时效性？（天气、订单状态等）
    前置过滤器 · 时效性查询缓存毫无意义甚至有害
  3. 用户的问题大多是固定的，还是天马行空的？
    命中率分析 · 命中率高 → 语义缓存才有价值
  4. 命中节省的成本，能否覆盖每次都要跑向量搜索的判断费？
    算账 · 这是语义缓存特有的"先交保护费"模式
  5. 团队是否有能力守住每一个坑（嵌入质量 / 阈值调试 / 度量选型）？
    人和能力 · 5 个坑要有人看护，否则就是定时炸弹
06

语义缓存的"经济账"

收益（命中时）

省下调大模型的 Token 费
省下首次向量搜索的成本
用户更快拿到答案

VS
代价（每次都付）

每个查询都要嵌入一次
每次都要跑一次向量搜索
命中或未命中都付这笔"判断费"

净赚 → 上 ｜ 净亏 → 不上

07

横向连接：同一个工具，不同的用法

语义缓存 vs RAG —— 底层都是「嵌入 + 向量搜索」，差别在哪？
RAG： 检索 → 填充上下文 → 还要调模型 → 返回 语义缓存： 检索 → 直接返回 → 不调模型 → 返回 // RAG 的检索是【帮模型干活】 → 模型还要跑 // 语义缓存的检索是【替模型干活】 → 模型可以不跑

🎯 工程师视角：工具是一回事，怎么用是另一回事。 同样的嵌入 + 向量搜索，放在请求路径的不同位置，就是两件性质完全不同的事。

嵌入向量在「文本数值化表达」家族中的位置
爷爷：文本的数值化表达 │ ┌─────────┼─────────┐ ▼ ▼ ▼ 词袋类 主题模型 嵌入向量类 ① One-Hot ④ LDA ⑥ Word2Vec ② TF-IDF ⑦ BERT 句向量 ③ Bag-of-Words ⑧ OpenAI Embeddings // 嵌入向量赢在哪？ // 它是第一个真正"理解意思"的数值化方法。 // 没有它 → 无法判断"语义相似" → 没有语义缓存。
